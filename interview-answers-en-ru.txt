3. HOW DO YOU TEST API PERFORMANCE? PROJECT EXAMPLE?
================================================================================

EN:
I use a layered approach:

1. Baseline metrics in production/staging: latency (p50/p95/p99), RPS, error rate,
   saturation (CPU, memory, DB connections, goroutines).

2. Load testing tools:
   - k6, vegeta, or hey for HTTP APIs
   - ghz for gRPC
   - Custom Go benchmarks for hot paths (BenchmarkXxx in *_test.go)

3. What I measure:
   - Throughput under target RPS
   - Latency distribution under load (not just average)
   - Resource usage and bottlenecks (DB, network, locks, GC pauses)
   - Degradation behavior when dependencies are slow

4. Process:
   - Define SLOs (e.g., p99 < 200ms at 1000 RPS)
   - Reproduce production-like data volume and payload sizes
   - Profile under load (pprof: CPU, heap, goroutine, mutex)
   - Fix bottleneck, re-run, compare

Example: In a payment gateway service (Go), checkout API p99 was ~800ms at peak.
pprof showed excessive DB round-trips (N+1). Added batch queries + Redis cache for
read-heavy lookups. After change: p99 ~120ms at same load. Validated with k6 and
monitored in Grafana for a week before full rollout.

2. Инструменты нагрузочного тестирования:

4. IMPROVEMENT APPROACH WHEN API DOES NOT WORK AS EXPECTED
================================================================================

EN:
Structured debugging, not guessing:

1. Reproduce: exact request, environment, version, correlation ID.
2. Observe: logs (structured), traces (OpenTelemetry), metrics (error rate spike?).
3. Narrow scope: client issue vs gateway vs service vs DB vs downstream dependency.
4. Check recent changes: deploys, config, migrations, feature flags.
5. Isolate: can you call the dependency directly? Is it intermittent?
6. Fix with minimal blast radius: hotfix vs rollback vs feature flag off.
7. Post-incident: root cause, action items, add test/alert to prevent recurrence.

For APIs specifically: validate contract (OpenAPI/proto), auth headers, timeouts,
payload schema, idempotency keys, and downstream circuit breaker state.

RU:
Структурированная отладка:

1. Воспроизведение: запрос, окружение, версия, correlation ID.
2. Наблюдение: логи, трейсы, метрики (скачок ошибок?).
3. Сужение: клиент / gateway / сервис / БД / внешняя зависимость.
4. Недавние изменения: деплои, конфиг, миграции, feature flags.
5. Изоляция: прямой вызов зависимости? Интермиттент?
6. Исправление с минимальным blast radius: hotfix / rollback / выключение флага.
7. Post-mortem: root cause, action items, тест/алерт против повторения.

Для API: контракт, auth, таймауты, схема payload, idempotency keys, circuit breaker.

5. EVENTUAL CONSISTENCY — ARE YOU FAMILIAR?
================================================================================

EN:
Yes. Eventual consistency means that after a write, all replicas/consumers will
converge to the same state, but not instantly. There is a window where reads may
return stale data.

Common in:
- Distributed databases (Cassandra, Dynamo-style)
- CQRS + event sourcing
- Cache-aside patterns
- Async messaging between services

Implications for design:
- UI must tolerate stale reads or show "pending" states
- Business rules must handle duplicates and out-of-order events
- Use versioning, timestamps, or "read your writes" strategies where needed
- Compensating transactions / sagas for cross-service workflows

RU:
Да. Eventual consistency — после записи все реплики/потребители сойдутся к одному
состоянию, но не мгновенно. Есть окно, когда чтение может вернуть устаревшие данные.

Типично в:
- Распределённых БД
- CQRS + event sourcing
- Cache-aside
- Асинхронном обмене между сервисами

Для дизайна:
- UI терпит stale reads или показывает «pending»
- Бизнес-правила учитывают дубликаты и out-of-order события
- Версионирование, timestamps, «read your writes» где нужно
- Compensating transactions / sagas для кросс-сервисных процессов

7. ANTI-CORRUPTION LAYER IN DB MIGRATION (2 DATABASES)
================================================================================

EN:
Yes, very useful. An Anti-Corruption Layer (ACL) translates between the old domain
model and the new one so that legacy concepts do not leak into the new system.

In a dual-DB migration:
- ACL sits between application code and both data stores (or between old and new services)
- Maps entities, field names, enums, and business rules
- Allows strangler-fig pattern: route traffic gradually to the new DB
- Protects new codebase from legacy quirks (nullable fields, inconsistent enums)

Without ACL, teams often copy bad schemas and coupling into the new system, making
the migration longer and riskier.

RU:
Да, очень полезен. Anti-Corruption Layer переводит между старой и новой доменной
моделью, чтобы legacy не «протекал» в новую систему.

При миграции между двумя БД:
- ACL между кодом и обоими хранилищами (или между сервисами)
- Маппинг сущностей, полей, enum, бизнес-правил
- Strangler-fig: постепенный перевод трафика на новую БД
- Защита нового кода от legacy-особенностей

Без ACL часто копируют плохие схемы и связность, удлиняя и усложняя миграцию.

8. SERVICE IS SLOW — WHAT INDICATORS / METRICS TO CHECK?

EN:

Infrastructure:

2. Distributed trace for slow request path
3. pprof under load (CPU, heap, goroutine, block)
4. Compare with baseline — regression after deploy?

10. GITHUB ACTIONS FOR ROLLBACK
================================================================================

EN:
Rollback in GitHub Actions is usually "redeploy a known-good artifact/tag", not
re-running a broken pipeline blindly.

Approaches:
1. Immutable artifacts: build once, push image with git SHA tag. Rollback workflow
   takes `image_tag` input and deploys previous SHA.
2. `workflow_dispatch` rollback job: select environment + previous release tag.
3. Revert commit on main → triggers normal CD pipeline (clean audit trail).
4. Blue/green or canary: shift traffic back to previous deployment in K8s/ALB.
5. Store last N successful deployment metadata (JSON artifact) for one-click rollback.

Example workflow sketch:
- `rollback.yml` on workflow_dispatch
- Inputs: environment, image_tag (or release version)
- Steps: kubectl set image / helm rollback / terraform apply previous state
- Post-deploy smoke tests + automatic alert if health check fails

Never rollback DB migrations blindly — need backward-compatible migrations or
separate rollback playbook.

RU:
Rollback в GitHub Actions — это «задеплоить известный хороший артефакт», а не
слепой перезапуск сломанного pipeline.

Подходы:
1. Immutable artifacts: образ с git SHA; rollback workflow принимает `image_tag`.
2. `workflow_dispatch` с выбором окружения и тега.
3. Revert коммита → обычный CD (чистый audit trail).
4. Blue/green или canary: вернуть трафик на предыдущий deployment.
5. Хранить метаданные последних N успешных деплоев.

Пример: `rollback.yml`, inputs environment + image_tag, kubectl/helm rollback,
smoke tests после деплоя.

Миграции БД откатывать вслепую нельзя — backward-compatible migrations или отдельный playbook.

17. EVENT-DRIVEN + CACHING — CONSISTENCY CONSIDERATIONS
================================================================================

EN:
- Cache invalidation is hard: TTL alone may serve stale data too long
- Prefer cache-aside with explicit invalidation on write events
- Or write-through / write-behind with clear consistency SLA
- Eventual consistency between DB, cache, and read replicas
- Use version numbers or timestamps in cache entries; reject stale writes
- Idempotent consumers so duplicate invalidation events are safe
- Consider CDC (Debezium) to keep cache in sync with DB truth
- Document acceptable staleness per use case (product catalog vs account balance)

- Версии/timestamps в записях кэша
- Идемпотентные consumers для дубликатов инвалидации
- CDC (Debezium) для синхронизации с БД

20 & 63. GO — INTERFACE IMPLEMENTATION
================================================================================

EN:
Go uses implicit (structural) interface satisfaction — no `implements` keyword.
A type implements an interface if it has all methods with matching signatures.

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type MyReader struct{}
func (m MyReader) Read(p []byte) (int, error) { return 0, nil }
// MyReader implements Reader automatically
```

Key points:
- Interfaces are satisfied implicitly — enables decoupling and easy mocking in tests
- Small interfaces (io.Reader, io.Writer) — "accept interfaces, return structs"
- nil interface gotcha: var err *MyError = nil; var e error = err → e != nil
- Empty interface `any` for generic containers; prefer generics (Go 1.18+) where typed
- Compile-time check: `var _ MyInterface = (*MyType)(nil)`

RU:
В Go интерфейсы удовлетворяются неявно (structural typing) — без `implements`.
Тип реализует интерфейс, если имеет все методы с нужными сигнатурами.

Важно:
- Неявная реализация — удобное мокирование в тестах
- Маленькие интерфейсы — «принимай интерфейсы, возвращай структуры»
- Ловушка nil interface: присвоение typed nil в interface даёт non-nil interface

21 & 42 & 56. GO — ARRAYS VS SLICES
================================================================================

EN:
Array: fixed length, value type, part of type `[N]T`. Passing copies N elements.
Slice: descriptor (pointer, len, cap) over underlying array; reference semantics.
Most Go code uses slices, not arrays.

```go
var a [3]int           // array, size is type的一部分
s := make([]int, 0, 10) // slice: len 0, cap 10
s = append(s, 1)       // may reallocate underlying array
```

Differences:
- Arrays cannot be resized; slices can grow via append (may reallocate)
- Slicing shares underlying array — mutations visible across slices (careful!)
- `len` vs `cap`: capacity is pre-allocated room before reallocation
- Passing slice to function passes header (cheap); array passes copy (expensive for large N)
- nil slice is valid (len=0); nil array is still `[0]T` with zero value

Performance tip: preallocate with `make([]T, 0, expectedCap)` to avoid repeated allocations.

RU:
Массив: фиксированная длина, value type `[N]T`, при передаче копируется.

Слайс: дескриптор (указатель, len, cap) над массивом; reference semantics.
В Go почти всегда используют слайсы.

Отличия:
- Массив не меняет размер; слайс растёт через append (возможна реаллокация)
- Слайсы разделяют underlying array — мутации видны везде
- len vs cap
- Передача слайса дешёвая; массива — копия
- nil slice валиден

Совет: `make([]T, 0, cap)` для уменьшения аллокаций.

27. DUAL WRITE IN MICROSERVICES — PATTERNS, "LISTEN TO YOURSELF"
================================================================================

EN:
Dual write problem: writing to DB and publishing event (or second store) without
atomicity — one can succeed, the other fail → inconsistency.

Solutions:
1. Transactional Outbox: write business data + outbox row in same DB transaction;
   separate relay publishes to broker (at-least-once, idempotent consumers).
2. Change Data Capture (CDC): DB is source of truth; Debezium streams changes to Kafka.
3. Saga: orchestrate steps with compensations.
4. "Listen to yourself" / read-your-own-writes via events: service consumes its own
   events to update read models or secondary stores — single writer path.

Avoid naive "write DB then publish" without outbox — it will break under failures.

RU:
Dual write: запись в БД и publish без атомарности → рассинхрон.

Решения:
1. Transactional Outbox + relay
2. CDC (Debezium) — БД source of truth
3. Saga с компенсациями
4. «Listen to yourself» — сервис обновляет read model из своих событий

Избегать наивного «сначала БД, потом publish» без outbox.

36. OUTBOX PATTERN (DATA CONSISTENCY)
================================================================================

EN:
Transactional Outbox solves dual-write: in one DB transaction, insert/update business
row AND insert row into `outbox` table with event payload. A separate process (polling
or CDC) reads outbox and publishes to message broker, then marks row as sent.

Guarantees: event is never published without DB commit; relay retries on failure.
Consumers must be idempotent (event ID as dedup key).

Variants: inbox pattern for incoming events; CDC instead of polling relay.

RU:
В одной транзакции БД: бизнес-данные + строка в `outbox`. Relay публикует в broker
и помечает отправленным. Consumers идемпотентны по event ID. Вариант: CDC вместо polling.

37. PREVENTING EXTERNAL API FAILURE FROM FAILING YOUR SYSTEM
================================================================================

EN:
- Timeouts on every outbound call (never infinite wait)
- Circuit breaker: stop calling failing dependency; fail fast
- Bulkhead: separate thread pools / connection limits per dependency
- Retries with exponential backoff + jitter (idempotent ops only)
- Fallback responses or cached stale data where acceptable
- Async processing: don't block user request on non-critical vendor call
- Rate limit your own outbound calls to avoid triggering vendor throttling
- Health checks that reflect dependency state; degrade features gracefully

RU:
Таймауты, circuit breaker, bulkhead, retry с jitter (идемпотентность), fallback/кэш,
async где возможно, rate limit исходящих, graceful degradation.

38. ARCHITECTURAL PATTERN WHEN EXTERNAL API FAILS
================================================================================

EN:
Combine:
- Circuit Breaker (stop hammering dead service)
- Retry + Timeout (transient failures)

- Queue-based async retry for non-urgent writes
- Saga with compensation if multi-step workflow
- Optional: multi-vendor failover if business critical (payments, SMS)

Circuit breaker + retry/timeout + кэш + async queue + saga; при критичности — failover

50. CURSORS IN QUERY LANGUAGES — WHY USEFUL?
================================================================================

EN:
Cursors iterate over a result set without loading all rows into memory at once.
Essential for:
- Large exports and batch processing (millions of rows)
- Stable pagination through changing datasets (vs OFFSET which skips rows inefficiently
  and inconsistently under concurrent writes)
- Streaming processing in application or DB driver

In PostgreSQL: `DECLARE cursor`, or keyset pagination (`WHERE id > $last_id ORDER BY id
LIMIT N`) is often preferred over OFFSET for performance.

Everyone uses them (or keyset equivalent) because they bound memory and provide
consistent iteration through large datasets.

RU:
Курсоры итерируют результат без загрузки всех строк в память. Нужны для больших
выгрузок, стабильной пагинации (лучше OFFSET при конкурентных записях), streaming.
В PostgreSQL часто предпочитают keyset pagination (`WHERE id > $last`). Ограничивают
память и дают предсказуемую итерацию.

63. CAN A MICROSERVICE PROCESS AN EVENT TWICE? IDEMPOTENCY
================================================================================

EN:
Yes — at-least-once delivery (Kafka, RabbitMQ with acks) guarantees duplicates possible.

Prevention:
- Idempotency key (event ID or business key) stored in DB with UNIQUE constraint
- "Processed events" table: insert event_id before handling; skip if exists
- Natural idempotency: PUT with same payload, debiting wallet with idempotent key
- Design handlers so repeated execution produces same final state
- Exactly-once semantics in Kafka are effectively "idempotent consumer + transactional offsets"
  within limits — still design for at-least-once

RU:
Да, при at-least-once доставке. Идемпотентность: event ID в UNIQUE таблице,
processed_events, бизнес-ключи, проектирование handler для повторного выполнения.
Exactly-once на практике = идемпотентный consumer.

64. CIRCUIT BREAKER — MAIN ADVANTAGE, CLIENT VS SERVER
================================================================================

EN:
Main advantage: fail fast and protect the caller (and the failing dependency) from
cascading overload. When failure rate exceeds threshold, breaker opens — calls return
immediately without waiting for timeout.

Benefits both sides:
- Client: doesn't waste threads/goroutines waiting; can return fallback or error quickly
- Server (failing): gets breathing room to recover instead of retry storm

Server-to-server: client service implements breaker on outbound calls (e.g., sony/gobreaker,
hystrix-style). It's primarily a client-side pattern protecting the calling service and
giving the callee time to heal. Server can also use rate limiting and bulkheads.

RU:
Главное: fail fast и защита от каскадных отказов. При открытом breaker вызовы не ждут
таймаут.

Клиент не тратит goroutines; сервер получает передышку от retry storm.

В server-to-server breaker на исходящих вызовах (gobreaker). В основном client-side
паттерн; на сервере также rate limit и bulkhead.

68. HOW DO YOU SET REASONABLE TIME ESTIMATES?
================================================================================

EN:
- Break work into tasks < 1–2 days each
- Reference similar past work (analogous estimation)
- Include: code, tests, review cycles, deploy, monitoring, documentation
- Explicitly add risk buffer for unknowns (integrations, new tech) — 20–50%
- Spike first if uncertainty is high (time-boxed investigation)
- Three-point estimate: optimistic / likely / pessimistic
- Re-estimate when new information appears; communicate early
- Track actual vs estimate to improve calibration
